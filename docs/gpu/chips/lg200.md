# LG200 Generation Profile

Values and capabilities of one generation.  Chapters elsewhere describe the
mechanisms; this page holds the numbers, and a future generation gets its own
profile page with the same section structure.

## Identity and scope

| Property | Value |
|----------|-------|
| Generation | LG200 (Loongson GPU, gen 2) |
| Shader instruction variants | 768 machine rows in 12 format families |
| Instruction word | two little-endian 32-bit words (`INST_LO`, `INST_HI`) |
| Driver generations in this family | LG210, LG220, LG300 (not covered here) |

## Pipes

A pipe is a command-processing engine with its own ring, its own command
vocabulary and its own completion source; [Host
Interface](../host/interface.md) describes how the kernel provisions them and who
owns each layer, and the per-pipe pages describe the vocabularies.  This
generation's pipes and their values are:

| Pipe | ICMD MOP | Cursors (write / read) | VMIDs | Owner | Completion |
|------|---------:|-----------------------:|-------|-------|------------|
| GPIPE | `0x01` (`BGQ`, `GQSZ`, `UBGQ`, `RESET`) | `0x18` / `0x1c` | 1..3 | graphics ring (DRM) | end-of-pipe event, IRQ source `0x01` |
| BPIPE | `0x02` | `0x30` / `0x34` | — | inner graphics commands, blits | end-of-pipe event |
| CPIPE | `0x03` (`BCQ`, `CQSZ`, `UBCQ`, `BCDB`, `UBCDB`) | `0x38` / `0x3c` | 4..7 | compute queues (KCD) | compute event, IRQ source `0x22` |
| XDMA | `0x04` (`BDQ`, `DQSZ`, `UBDQ`) | `0x20` / `0x24` | — | linear copy and fill | transfer event, IRQ source `0x23` |
| DPIPE / EPIPE | `0x0c` / `0x0d` | present in the interface | — | decoder and encoder routes, owned by LG210 | not assigned on LG200 |

VMID 0 is the kernel/control context; graphics uses the next three, and compute
queues the remaining four.  Compute queue IDs 0-7 are exposed.

The execution unit behind the pipes is the stream processor, whose structure is
in [Execution Model](../concepts/execution-model.md#the-stream-processor).

## Address space and execution limits

| Property | Value |
|----------|-------|
| Page-table entry size | 64 bits, four-level walk |
| Shader code size field | 16-bit byte count in the shader-info record; a complete instruction stream is a multiple of 8 bytes |
| Scalar registers | 102, `s0..s101`; the low twelve are reserved, see [Registers and Allocation](../shader/registers.md) |
| Vector registers | 256, `v0..v255` |
| Lane-mask registers | 4, `p0..p3`, plus a scalar allocation window |
| Wave size in use | 32 lanes |
| Fragment attributes | 32 attribute-map entries |
| Color attachments | 8 surface records; one depth surface record |
| Viewports | 16 viewport records |
| Shared-memory (LDS) size | UNRESOLVED — the shader-info record carries the allocation and every established path leaves it zero, so the usable size is not communicated |

The wave size is 32 lanes, established twice independently: the vendor's
reference producer emits `.wave_size: 32`, and a launch's generated group count
equals `ceil(lanes / 32)`, which pins the divisor to 32.  Whether 32 is an
architectural maximum, and how many waves a unit can hold, are `UNRESOLVED`.

## Graphics state

The graphical payload is one 512-dword state object inside a fixed envelope.
[The State Object](../graphics/state-object.md) maps all 33 of its blocks, marks
which of them a working path writes, and gives the field layouts and enums.

## Shader stages

| Slot | State offset | Shader type value | Role |
|------|-------------:|------------------:|------|
| VS | `0x540` | not assigned | standalone vertex |
| HS | `0x5a0` | not assigned | hull / tessellation control |
| DS | `0x600` | 3 | tessellation evaluation, or the ordinary vertex role |
| GS | `0x660` | 4 | geometry |
| SS | `0x6c0` | 6 | streamout |
| PS | `0x720` | 5 | fragment |

## Instruction families

| Family | Rows | Format families |
|--------|-----:|-----------------|
| Vector ALU | 374 | `vop`, `vop-imm`, `shared-memory` |
| Scalar ALU | 119 | `sop`, `sop-imm-control` |
| Memory and image | 138 | `smem`, `tex-buffer`, `flat`, `shared-memory` |
| Atomic | 97 | `tex-buffer`, `flat`, `shared-memory` |
| Control prefix | 20 | `sop-imm-control`, `jump-stack`, `shared-memory`, `prefix` |
| SIO and export | 17 | `sio-id`, `sio-imm` |
| Interpolation | 3 | `vop` |

A family is a grouping of the reference chapters, not an encoding property: the
two are orthogonal, so a family may draw on several formats and a format may
serve several families.  Four rows sit across the boundary — `v_bperm_sm_b32`
and `v_perm_sm_b32` are permutes over the workgroup allocation, and
`copy_sm_from_global` and `copy_sm_to_global` move blocks between it and global
memory — and each is documented in the chapter that describes its mechanism.
